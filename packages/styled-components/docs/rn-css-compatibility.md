# React Native CSS Features Compatibility

This is a living index of modern CSS capabilities and their current state on the React Native path. Features are grouped into what works today, what we polyfill, and what still needs upstream React Native support to become usable.

The goal is transparency: if you rely on something in this document, you can see whether it runs today, how we handle it under the hood, and what would need to change upstream to move a "not supported" row into the "polyfilled" or "native" column.

The tables describe iOS and Android. On the web (react-native-web) the browser renders your CSS, so support follows the browser; [On the web](#on-the-web-react-native-web) lists the few mappings styled-components adds there.

If a feature you need isn't listed, or the workaround section needs updating, open a comment or pull request to extend this file.

## Status snapshot

As of React Native 0.85:

- Many modern CSS features work natively, including CSS string transforms, box-shadow with spread/inset, filter chains, gradients, slash-alpha colors, `hwb()`, `mix-blend-mode`, `isolation`, `cursor`, `display: contents`, logical margin/padding/inset longhands, and several logical border longhands.
- Many features that React Native does not parse natively are polyfilled by styled-components on iOS and Android: either converted before styles reach React Native or resolved against the live device environment.
- Other features still require upstream React Native work to support meaningfully. This document is a contract with the community: when one of those ships, we wire it up and move the row out of the unsupported section.

## Works natively in React Native 0.85

- `aspect-ratio`, `backface-visibility`, `border-radius`, `box-sizing`, `display: contents`, `object-fit`, `opacity` (a percentage such as `50%` converts to the equivalent number), `outline-offset`, `overflow`.
- `background-image: linear-gradient()` / `radial-gradient()` + `background-size` / `background-position` / `background-repeat`.
- `box-shadow` with offset, blur, spread, inset, and multi-shadow lists.
- Colors: hex, `rgb()` / `rgba()`, `rgb(r g b / a)` slash-alpha, `hsl()` / `hsla()`, `hwb()`, named colors, `transparent`.
- `cursor`, `direction`, `mix-blend-mode`, `pointer-events`, `user-select`.
- `isolation: isolate` scopes descendant `mix-blend-mode` to the element's own compositing group on every target. Android has no isolation style key, so styled-components also lifts React Native's hardware-texture layer prop to create the isolated surface; without it, blended descendants composite against the page background there.
- `filter: blur() brightness() contrast() drop-shadow() grayscale() hue-rotate() invert() opacity() saturate() sepia()` chains. On iOS, RN 0.85 requires the SwiftUI filter backend (`ReactNativeReleaseLevel` experimental) for `blur`, `saturate`, `hue-rotate`, `grayscale`, `contrast`, and `drop-shadow`; `brightness` and `opacity` work without that flag. Caution: while a gated filter function is mounted on iOS at the default release level, descendants' `mix-blend-mode` also stops compositing against the backdrop (device-verified); development builds warn once when this applies.
- Flex: `flex-grow` / `flex-shrink` / `flex-basis`, `align-items`, `justify-content`, `align-content`.
- Gap: `gap` / `row-gap` / `column-gap`.
- Logical margin / padding / inset longhands in the inline and block axes, plus their `-top` / `-bottom` / `-left` / `-right` counterparts. React Native also supports logical border colors/radii and start/end widths; styled-components fills the remaining `border-inline-*` / `border-block-*` CSS syntax below.
- Position: `absolute` / `relative`, plus `static` on the new renderer.
- `transform: translateX(10px) rotate(45deg) scale(1.2) matrix(<9 or 16 numbers>)` as a CSS string or transform array. React Native 0.85 accepts `matrix` arrays of 9 or 16 numbers, but the CSS string parser does not support the `matrix3d()` function name, and non-zero translate lengths need units. On Android, `skewX()` / `skewY()` parse but React Native drops the rendered skew; development builds warn once.

## Polyfilled by styled-components

On iOS and Android these work in your style templates even though React Native doesn't parse them natively. styled-components either rewrites the value before handing it to React Native, or re-evaluates it on each render against the live environment. On the web the browser handles the same CSS itself.

### React Native pseudo-states (equivalent to CSS pseudo-classes)

On the web these are ordinary CSS pseudo-classes (`:hover`, `:focus`, `:active`, ...) matched by the browser on any element. On iOS and Android, `:active`, `:focus` and `:hover` resolve through the live state React Native provides, which only `Pressable` (or a custom component forwarding its style to one) supplies. On other elements (`View`, `Text`, etc.) those rules stay inert with a one-time development warning, since those hosts have no press / hover / focus state to track. `:disabled`, `:enabled`, `:read-only` and `:read-write` read the props you pass instead; the rows below say which elements each one can match, and a rule an element can never match (`:disabled` on a `View`) also warns once. A rule fenced behind a non-matching media query (e.g. web-only `@media (hover: hover)` rules) stays silent.

| CSS                       | React Native mapping                                                                                                                                                                                                                                                                                                                                           |
| ------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `&:active`                | `Pressable` while it is pressed.                                                                                                                                                                                                                                                                                                                               |
| `&:disabled`              | Each component's own rule for "disabled". `Pressable` and custom components: the `disabled` prop. `TouchableOpacity` and `Text`: `disabled`, else `aria-disabled`, else `accessibilityState.disabled`. `TouchableHighlight`: `disabled`, else `accessibilityState.disabled`. `Switch`: `disabled` on iOS; `disabled`, else `accessibilityState.disabled` on Android. `TextInput`: `disabled` or `aria-disabled`. |
| `&:enabled`               | Every element that is not disabled, including `View` and `Text`. Unlike [the CSS definition](https://drafts.csswg.org/selectors-4/#enableddisabled), which limits `:enabled` to elements that can be disabled, this is the exact complement of `:disabled`.                                                                           |
| `&:read-write`            | A `TextInput` that is not disabled, not `aria-readonly`, and editable by React Native's own rules (`readOnly` wins over `editable`). A custom component only when it is not disabled and you pass `readOnly={false}`, or `editable={true}` without `readOnly`. See [`:read-write`](https://drafts.csswg.org/selectors-4/#rw-pseudos).                                                               |
| `&:read-only`             | Every element that is not `:read-write`, so a `TextInput` with `readOnly`, `editable={false}`, `aria-readonly` or `disabled`, and every `View`, `Text` and `Pressable`.                                                                                                                                                                                         |
| `&:focus`                 | `onFocus`/`onBlur` on focusable inputs.                                                                                                                                                                                                                                                                                                                        |
| `&:hover`                 | `Pressable` hover state (desktop) or `onHoverIn`/`onHoverOut` (iOS pencil / desktop-like).                                                                                                                                                                                                                                                                     |
| `&:active:not(:disabled)` | Compounds of pseudo-classes and `:not()` of one are supported: every term must match, so this applies while pressed and enabled. `&:hover:enabled` works the same way, and so do compounds that start with an attribute or structural selector (`&[data-on]:hover:not(:disabled)`, `&:first-child:hover:enabled`). A negated attribute can sit anywhere in a chain that starts with a pseudo-class or an attribute (`&:hover:not([data-x])`). Two forms are skipped on iOS and Android with a development warning while the web applies them: a negated attribute after a position selector (`&:first-child:hover:not([data-x])`), and a negated class (`&:hover:not(.icon)`), since native elements have no class names. In a selector list (`&:hover, & .icon`) each member is judged on its own: supported members apply, and an unsupported member is skipped with a development warning naming it.                                                                                                                                                                                         |

What to know on iOS and Android:

- `accessibilityState={{ disabled: true }}` alone matches `:disabled` on `TouchableOpacity`, `Text`, `TouchableHighlight` and `Switch` (Android only), the same elements React Native treats as disabled. React Native Web ignores it, so it does not match on the web.
- `aria-disabled` alone matches `:disabled` on `TouchableOpacity`, `Text` and `TextInput`. On `Pressable`, `TouchableHighlight`, `Switch` and `View` it does not.
- React Native's own components are recognized as themselves, not by name: your own component named `Button` or `Text` follows the custom-component rules above. An animated wrapper (`Animated.createAnimatedComponent(Text)`) counts as the component it wraps.
- A `transition` does not animate a `:disabled` or `:enabled` change: the values snap.
- A pseudo-class rule (`&:active`, `&:disabled`, `&:read-only`, ...) applies after any attribute-selector rule (`&[data-x]`) whatever the source order. In a browser, source order decides between rules of equal specificity.
- No pseudo-class rule (`:disabled`, `:enabled`, `:active`, ...) on `TouchableWithoutFeedback`, `TouchableNativeFeedback` or `Button` applies: they never apply the `style` you give them.
- `interactivity: inert` never matches `:disabled` and does not change `:read-write`.

### Image and ImageBackground

- **`Image`**: authored layout and paint (`width`, `height`, `margin`, `opacity`, `borderRadius`, `tintColor`, `resizeMode` / `objectFit`, filters and shadows on the view) map to RN `Image` / wrapper styles like any other view-backed component.
- **`ImageBackground`**: the outer container accepts normal **view** styles (positioning, flex, padding). The bitmap layer uses React Native’s **`imageStyle`** (or equivalent) for `resizeMode`, `borderRadius` on the image, `tintColor`, and background image sizing; layered CSS `background` from templates may split between **container** and **image** styles after compilation. Prefer explicit layout on the wrapper when you need predictable clipping or padding around the image.

### TextInput, Switch, and Button (style vs props)

- **`TextInput`**: treat **box model**, **typography**, **colors**, **outline**, and **opacity** as normal template CSS when they map to RN style keys. **Placeholder text and color**, **caret / selection colors**, **keyboard type**, **secure text entry**, **return key behavior**, **autocorrect**, **multiline** scrolling, and similar controls are **React props** (or platform-specific props), not something to spell as non-standard CSS in templates. Some real CSS (for example `caret-color`) may map to RN props where the platform exposes them; see the polyfilled and native rows above when listed. **`disabled`** (or `aria-disabled`) makes the input non-editable, unfocusable and announced as disabled, and it wins over `editable`, `readOnly` and `tabIndex`; it is also what `&:disabled` matches on a `TextInput`. See [`:disabled`](https://drafts.csswg.org/selectors-4/#enableddisabled) and [`:read-only` / `:read-write`](https://drafts.csswg.org/selectors-4/#rw-pseudos).
- **`Switch`**: **track and thumb colors**, **disabled** state, and iOS background tint are **props**. Layout around the control (margins, flex alignment) is **style** on the same component or a parent `View`.
- **`Button`**: RN’s `Button` is not a general-purpose styled surface. For CSS-shaped controls, compose **`Pressable` (or `Touchable*`) plus `Text`** so template CSS applies to ordinary view and text children.

## On the web (react-native-web)

On the web, `styled-components/native` compiles your styles like regular `styled-components` and the browser renders the CSS. The iOS and Android polyfills do not run, so a feature works when the browser supports it. That includes `light-dark()`, viewport units, mixed-unit `calc()`, modern color functions, `color-mix()`, `@property`, `@container`, `@keyframes`, `animation`, `transition`, `position: sticky`, `display: grid`, anchor positioning, and pseudo-classes such as `:hover` and `:has()`. `prefers-reduced-motion` media queries apply as you author them; styled-components does not shorten durations on its own.

The bridge adds these mappings:

## Routing values onto wrapped components with `attrs`

Some CSS properties only target a specific React Native primitive on native: `text-overflow` and the line-clamp surface drive props on `<Text>`; `accent-color` drives `<Switch>`; `overscroll-behavior`, `scrollbar-width`, and `scroll-snap-type` drive `<ScrollView>` props. The default polyfill lifts the right props automatically when you style one of those primitives directly. These properties, and the others that set a component prop (`object-fit`, `caret-color`, `text-wrap`, `hyphens`, `isolation`, `interactivity`), work at the top level of a component only: inside a nested rule (`&:active`, `&[data-on]`, `&:first-child`, `${Parent} &`, `@media`, ...) they are dropped on iOS and Android with a development warning.

When you wrap a third-party component instead (e.g. a Slider, Checkbox, ProgressBar, BottomSheet), you can route the resolved CSS value onto whatever prop the wrapped component expects using the function form of `.attrs(...)` with the AST bridge. The second argument exposes `peek(key)` (read) and `pop(key)` (read and consume).

```tsx
import Slider from '@react-native-community/slider';
import styled from 'styled-components/native';

const ThemedSlider = styled(Slider).attrs<{ thumbTintColor?: string }>((_props, ast) => ({
  thumbTintColor: ast.pop('accentColor') as string | undefined,
}))`
  accent-color: red;
`;
```

`pop('accentColor')` returns the resolved value (a string, a theme token, or a `PlatformColor` for `accent-color: auto`) and removes it from the style bag so it doesn't end up as an unrecognized style key on the wrapped component. Use `peek` if you also need the value to stay in the style. Both accept the kebab-case or the camelCase spelling of a property (`'accent-color'` or `'accentColor'`) on every platform. The same pattern works with any CSS property: write the standards-compliant declaration in the template, route the value onto whichever prop the wrapped component actually reads.
